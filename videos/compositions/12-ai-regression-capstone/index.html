The capstone combines a defensible regression plan with AI-assisted implementation and
actual execution evidence. Choose your primary language and keep the same local
contract. Your required business cases are successful transfer, insufficient funds,
and sequential idempotent replay. Add the delayed ledger observation, a focused UI
error mock, and the hybrid terminal comparison as separately labeled coverage. Produce
tests whose assumptions, business assertions, ownership, and observed outcomes you can
explain and reproduce.
Start by supplying the contract, relevant source files, exact accessible labels,
runner configuration, and a sanitized example response. Ask AI to list unresolved
facts before proposing implementation. This exposes unsupported endpoints and helper
methods. The prompt excerpt on screen is reusable, but attach the actual evidence it
requests. A model cannot inspect an omitted file merely because the prompt mentions
its name. Keep any missing input marked as unresolved until you or the model can
inspect a reliable source.
Ask for a matrix connecting each business risk with setup, action, authoritative
observation, and expected result. Require the three core cases and give their exact
values. For the distributed extension, distinguish canonical transfers from the
delayed ledger endpoint. For the terminal extension, state that the screen presents
the same in-memory account data. Review the matrix yourself before generating code.
This is the point where a missing no-debit assertion or a false independent-mainframe
claim is easiest to correct, while the design remains visible.
Generate the successful case before asking for every extension. Specify the chosen
runner and require setup, authentication, accessible UI actions, server assertions,
evidence capture, and targeted cleanup. Ask for project changes with imports and
commands, not just a fragment that assumes invisible helpers. Review and run this
first case. Reuse its fixture for the other cases. If the generated code fails to
compile, fix that implementation issue while preserving the business contract; do not
record the application as regressed because an invented method was rejected.
When translating the case, ask AI to preserve the evidence matrix while adapting
lifecycle and reporting to the target runner. TypeScript uses Playwright Test
fixtures, Python uses pytest fixtures, and Java uses its explicit JUnit resource
ownership. Do not copy configuration flags across languages without checking that the
target runner supports them. Require explanations and check official documentation for
uncertain APIs. Then execute each language separately. A successful TypeScript run
does not establish that a generated Java or Python translation was discovered or
executed correctly.
For the hybrid case, provide the existing adapter rather than asking AI to invent a
mainframe connection. Specify the exact reference flow, terminal deadline, process
timeout, structured output fields, and cleanup sequence. Require argument arrays when
invoking the adapter from another language. Keep the terminal's simulation flag and
shared data source explicit in the assertions and report. This prompt should produce
orchestration around a known boundary. It should not create hostnames, credentials,
panel identifiers, or claims about systems that are absent from the local laboratory.
Review the generated suite against a fixed checklist. Does each attempt own its data
and session? Does success verify the correct account, amount, currency, and count?
Does rejection prove no business effect? Does replay preserve one key and body while
checking one debit and record? Does delayed polling only read state? Does the terminal
assertion match the same reference? Ask AI to identify concrete omissions with source
locations, then verify. A polished explanation cannot compensate for a missing
assertion in the actual test code.
When a test fails, provide the contract, actual error, relevant trace observations,
and state snapshot. Ask AI to separate facts from hypotheses and propose the smallest
check that distinguishes likely causes. Explicitly protect the monetary and count
assertions. Do not ask for a green run at any cost. A useful response may reveal an
incorrect fixture, an outdated locator, or a genuine implementation defect. Apply only
a justified change, then rerun the affected case and preserve the evidence that shows
whether the diagnosis held.
Run the three core cases first in the healthy local environment and inspect actual
test discovery and outcomes. Then run the delayed projection, mock, and hybrid cases
under their declared boundaries. Execute the controlled defect case separately and
retain its expected failure evidence. Record the application variant, language,
browser, test selection, and artifact locations for every run. Keep installation and
service-startup failures distinct from business regressions. This order keeps the
evidence package's environments and intended outcomes understandable.
Ask AI to summarize the actual results you supply, with links to artifacts and
explicit limitations. Require it to separate generated, reviewed, executed, passed,
failed, and blocked work. The final report should name the tested environment and
avoid claiming hosted CI execution unless a real pipeline result exists. Include the
terminal's shared local data source and the sequential scope of idempotency. These
limits help another engineer identify missing coverage without overestimating what the
tests exercised.
Score five areas from zero to two: business coverage, isolation, review of AI
assumptions, execution and diagnosis, and reporting of integration boundaries. Eight
out of ten is the target, with mandatory gates: no fabricated results, no leaked
sensitive data, and no weakened business assertions. Missing execution evidence
remains incomplete even when the design is strong. Review a partner's submission and
ask them to explain one failing case. The explanation should connect a concrete
observation to the original requirement, beyond repeating an error message.
Finish by selecting one next increment based on an uncovered risk: concurrent replay,
a real authorized recovery scenario, broader browser coverage, or another business
rule. Define its expected behavior and evidence before generating more code. Preserve
the core suite and its reproducible fixture design as the baseline. Combine AI
assistance with careful contracts, browser automation, distributed observations,
terminal orchestration, and honest reporting. Your final deliverable is the executable
work and its measured evidence, together with a clear account of what it still does
not prove.
