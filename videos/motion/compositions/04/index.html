This episode builds the Java equivalent using Playwright with JUnit. Start by
separating the browser library from the test runner. Playwright controls pages and
performs its locator assertions; JUnit organizes test execution and records test
outcomes. Maven supplies dependencies and launches the configured test process. Those
responsibilities do not become identical merely because the TypeScript edition
packages them together. Your job is to preserve the three business cases while making
resource ownership, assertion choices, and reporting explicit in the Java project.
Open the supplied Maven project and inspect the versions fixed in its project file.
Confirm which JSON library it includes, because response parsing examples must match
that library. The working hybrid example uses Gson; an example using Jackson needs its
own dependency and imports. Also inspect the browser channel configuration before
launching. Run Maven's version command to check the selected Java installation. If the
project does not compile, treat compiler errors as implementation feedback rather than
evidence that the application violated a transfer rule.
For the classroom, begin with sequential tests. A test may own Playwright, the
browser, and its context through resource blocks, as in the hybrid example. A larger
suite can use JUnit lifecycle methods while keeping one fresh context per case.
Whichever structure you choose, draw who closes each object. Avoid a static page
shared across tests. Its session, open dialogs, and navigation state can leak between
cases even when the test methods look independent in the source file and have
different names.
The excerpt shows the central context boundary inside an existing browser lifecycle.
Set the local base address when creating the context, then obtain its page.
Authentication happens on this context before protected navigation. Closing the
context releases its pages and browser session together. In a lifecycle method, the
corresponding cleanup belongs in the matching after method; in a resource block, Java
manages closing. Do not mix the two ownership approaches accidentally and leave an
object alive because each layer expected another layer to close it.
Post the synthetic fixture credentials through the context's request client. Check the
response status before reading the transfer page. The displayed request options carry
only the business login data; the local test hook key belongs on preparation requests.
By keeping those responsibilities separate, your Java test reflects the same
authorization model as the other language versions. If login succeeds but navigation
appears anonymous, inspect cookie scope and the base address instead of inserting
credentials into unrelated requests or bypassing the protected page entirely.
After selecting the source and beneficiary, fill the amount field and submit through
the accessible button. Use Playwright's assertion import for the visible balance,
because it provides locator-aware waiting. JUnit's ordinary equality assertion remains
appropriate for values you already obtained from an API response. These assertions
serve different observations, so inspect the imports when AI generates a test. A
method named assertThat from another library may have entirely different behavior even
if the surrounding Java code looks familiar and the editor offers an automatic import.
Fetch the source account through the same context and verify the successful response
before parsing its body. The excerpt uses Gson, matching the supplied hybrid Java
project. Compare the balance in minor units and preserve the source identifier in your
report. Next, read the canonical transfer collection and check its count and complete
business fields. Parsing a number is not enough if the query selected the wrong
account. This is why fixture identifiers remain visible through the action and every
following assertion.
Create separate fixtures for the rejection and replay tests. For rejection, verify the
business error, unchanged balance, and empty transfer list. For replay, send the same
request body and key twice, verify the creation and replay response statuses, and
compare their identifiers. Keep the final balance and count assertions even when both
identifiers match. Java's request option objects do not create idempotency by
themselves; the server contract interprets the key. Make that relationship explicit in
the test name and review the generated request construction carefully.
Start tracing before the browser actions you want to diagnose, then stop and save it
before closing the context. The excerpt shows the lifecycle calls. Your fixture or
JUnit extension decides when to retain the artifact and how to name it per test. Keep
the JUnit outcome alongside the trace, because the library trace is not a replacement
for the runner's assertion report. Verify this arrangement using an actual failure
rather than assuming a configured filename guarantees a useful diagnostic artifact.
Only add parallel execution after the sequential suite is reproducible. Playwright
Java objects should remain on their owning thread unless you implement the required
synchronization. Give each parallel execution its own Playwright instance and keep
calls on that thread. This is separate from data isolation: independent browser
objects can still collide when they mutate one shared account. Review both the thread
ownership and fixture identifiers before increasing concurrency, and keep failures
attributable to one test attempt rather than a mixture of overlapping sessions.
Run the selected Maven test and inspect its Surefire reports. A successful compilation
is only the preparation stage; the result must show that the intended test method
actually executed. Confirm the number of tests and inspect failures or skipped cases.
If a browser or terminal dependency is unavailable, keep that limitation in the
report. For hybrid work later, a Java test may invoke the Python adapter as a bounded
subprocess, but Java still owns the final assertion about the returned correlation and
business values.
Place the Java, Python, and TypeScript evidence matrices beside each other. Each
should describe the same starting balance, transfer amount, rejection behavior, and
single-effect replay. The lifecycle, configuration, and artifact commands differ; the
business promise does not. Explain why you used a locator assertion for the browser
and a value assertion for parsed JSON. Then point to cleanup and the actual result
files. The skill is adapting test architecture to a language without quietly weakening
